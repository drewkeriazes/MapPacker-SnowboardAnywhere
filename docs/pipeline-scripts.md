# Pipeline scripts

Every script in `pipeline/`, what it reads and writes and its options. Moved from the game's
[`docs/developer-guide.md`](https://github.com/drewkeriazes/SnowboardAnywhere/blob/main/docs/developer-guide.md) in FEAT-242 (SnowboardAnywhere#561), with paths for the
resort folders (FEAT-244). How to build a resort end to end: the README > Build a resort; the rules for working here: `CLAUDE.md`.

Flow: `resort.py resolve` and `plan` -> `resorts/<slug>/<slug>.json` -> `gen_manifest.py` -> `manifests/<slug>.json` -> `fetch.ps1` -> `raw/<slug>/` -> `build_pack.py` -> `packs/<slug>/`.

- `resort.py resolve "<name>" [--id <id>] [--with <name or id>] [--alone] [--slug <slug>]` (FEAT-223, EPIC-15) finds the ski area in OpenSkiData by name (case and accent insensitive; exact names first, a match without lifts drops out when another has them). Several matches: prints them and stops, `--id` picks. A neighbour with lifts that reaches into the box (closer than the buffer plus 500 m: Snowbird and Alta, Big Sky and the Yellowstone Club) or is sold with it (same website within 3 km: Boston Mills and Brandywine): stops and asks for `--with <name>` (one pack over both, named "Boston Mills / Brandywine") or `--alone` (the neighbour's runs and lifts go into `exclude` by OSM id). No match: the closest names. Writes `resorts/<slug>/<slug>.json` with the identity fields, `lonlat_bbox` (the area's polygon, lifts and runs) and an `openskidata` block; a hand-written config (no `openskidata`) is refused without `--force`.
- `resort.py plan <slug> [--no-nodes]` derives the rest: CRS and zone from the centre (NAD83 UTM in the US, WGS84 elsewhere), `buffer_m` = 0.3 x the box diagonal between 500 and 1000 m, `utm_bbox` (to 100 m) and `origin`, `elevation_range_m` from Mapterhorn z12, 1 m DEM coverage and projects from TNM Access, EPT datasets from the usgs.entwine.io boundaries (the one covering most, then extras for the strip it misses, clipped to it plus 500 m) with the depth whose node spacing is under 3.2 m (`lidar.far` on every resort, at the depth under 4.5 m), flight dates and QL from the 3DEP work unit index, NAIP from Planetary Computer STAC (the newest item per quarter quad), the Geofabrik extract (`osm`), `terrain_status_url` when the Internet Archive has the resort's Vail Resorts terrain status page, attribution and `tier`. Walks the EPT hierarchy for the node lists (about 1.5 minutes; `--no-nodes` skips it), writes the config, the node lists and `resorts/<slug>/<slug>-plan.md`, the data plan (layer, source, year, resolution, items, size, tier) to read before the fetch; `start_run` stays empty. Fields set by hand (`start_run`, `grooming_aliases`, `notes`, hand `exclude` entries) survive a re-plan.
- `resort.py add "<name>" [resolve's options] [--from <stage>] [--stop-after <stage>] [--force <stage>|all] [--raw-root <dir>] [--out <dir>] [--email <address>] [--no-publish] [--review-plan]` (FEAT-224) runs one resort from its name to a published pack, launched by `add_resort.cmd "<name>" [options]` in the repo root (which passes `--review-plan`: the first run stops after a new plan so Drew reads it before the fetch). Stages: `resolve` (skipped when the config is already planned for the same ski areas and left-out neighbours; a hand-written config is refused unless `--force resolve`), `plan` (skipped when `<slug>-plan.md` is there), then `fetch` (`build_resort.py` nodes to grooming), `build` (build and index), `report`, then the DATA-022 gate is printed (every MVP line that holds the pack back, with its detail), `ride` (`npx vite build`, then `game/tools/shoot.mjs <slug>` with `SHOT_PACKS` on the pack's folder: the pack must load, ride and fly with no page error; recorded per pack build in `<raw>/shots/ride.json`, stills there too) and `publish` (`publish_pack.py --tier <config tier>`, skipped when the resorts repo's `catalog.json` already has this build; status `preview` unless the report passes). `--force` takes `add`'s or `build_resort.py`'s stage names. Tests: `tests/test_resort_add.py`.
- `resort.py compare <slug>` plans a hand-written config's resort again from its name and lists the differences; writes nothing. The big index files (OpenSkiData areas, lifts and runs; the entwine boundaries; Geofabrik) are cached in `raw/_index/` (`--cache`, `SBA_INDEX_DIR`) for 30 days (`--refresh`). Tests: `tests/test_resort_plan.py` offline; `SBA_NETWORK=1` adds the real-host checks (Vail, Breckenridge and Big Sky against their hand configs, Boston Mills), on Drew's PC.

- `resorts/<slug>/<slug>.json` resort config (origin, UTM bbox and zone, rings, NAIP items, lidar nodes). Optional keys: `osm` and `openskidata` (written by `resort.py`, read by nothing else yet), `tier`; `lidar.extra`, more EPT datasets for the parts the main one misses, each with its own `nodes_file` and an optional `utm_bbox` clip (Big Sky's east strip; they download to `raw/<slug>/ept/<dataset>/`); `exclude`, members-only areas whose runs and lifts the build drops (`{"name", "osm_way": <id>}` for a polygon in `osm/ski.json`, `{"name", "lonlat": [[lon, lat], ...]}`, or `{"name", "osm_ways": [<id>, ...]}`, the area's own run and lift ways as `resort.py resolve --alone` writes them; ways tagged `access=private` go anyway, `osm_filter.py`); `treeline_m`, to override the measured treeline. Resorts so far: `vail`, `breckenridge`, `bigsky` (DATA-021, UTM 12N).
- `gen_manifest.py <slug>` writes `manifests/<slug>.json`, the download list (needs `pip install pyproj`), stamped with `manifestVersion` (bump `MANIFEST_VERSION` when the manifest gains a layer). The slug is required (it used to default to `vail`). `manifest_items(cfg, resorts_dir)` is the same list as a function (`resort.py plan` sizes the download with it).
- `build_resort.py <slug> [<raw_dir>] [<out_dir>] [--from <stage>] [--stop-after <stage>] [--force <stage>|all] [--email <address>] [--gate] [--dry-run]` (FEAT-175 step 3) builds a resort end to end, launched by `build_resort.cmd [slug] [raw_root]` in the repo root. Stages in order: `nodes` (`ept_select.py`), `manifest` (`gen_manifest.py`), `fetch` (`fetch.ps1`), `landfire` (`fetch_landfire.mjs` EVT, EVC and EVH; US only; LFPS wants an email: `--email`, `LANDFIRE_EMAIL` or a prompt), `grooming` (`fetch_grooming.py`, when the config has `terrain_status_url`), `build` (`build_pack.py`), `content` (`gen_content.py`: the start and the menu shots), `attract` (the game's `game/tools/auto_attract.mjs` with `SHOT_PACKS` at the pack's folder, after `npx vite build`: the menu still and ghost takes; on the GPU), `spots` (the game's `tools/propose_spots.py --shoot`: 10 proposed compare spots with game stills, written into the game checkout's `docs/compare/<slug>/`, once, while the resort has none there), `index` (`packs/index.json`) and `report` (`pack_report.py --raw`). `attract` and `spots` skip, saying so, without a game checkout that has those tools (`paths.game_repo`); an `attract/` that is hand-made is left alone, and `auto_attract.mjs` exiting 1 (a rider crashed, a page error) is a warning, not a stop. `raw_dir` defaults to `SBA_RAW_ROOT/<slug>`, else `raw/<slug>` in the main checkout, which every worktree shares, and must end in the slug (fetch.ps1 writes `<RawDir>\<slug>`), `out_dir` to `packs/<slug>`. Each stage's input fingerprint is kept in `<raw_dir>/build_resort.json` and a stage is skipped while it is unchanged: the config and node lists for the manifest, the manifest's items for the fetch (a new layer fetches again, only what is missing), the box for LANDFIRE (a moved box fetches the clips again with `--force`), and config, manifest, raw data and the code that builds the pack (`pipeline/` without tests, configs, manifests and the tools around the build; uncommitted changes count by content) for the build. The first run adopts what is already on disk, and a pack counts as built when its `meta.json` is this format and its `pipeline` commit has the same build code, so an existing resort is not walked, fetched or built again. Before the build, the raw data is checked, also when the fetch was skipped: every layer there, land cover (WorldCover, ETH canopy) and `osm/pistes_wide.json` unless the config sets `landcover.enabled: false`, `ept_far/` when it has `lidar.far`, `names/` in the US (FEAT-235), and the OSM files real JSON with elements, not an Overpass error page; a gap stops with "run again with `--force fetch`". An existing manifest is adopted only when it carries this `MANIFEST_VERSION` (an older one is made again, and the fetch gets the layers it lacked: Breckenridge's predates land cover); the fetch and build fingerprints hash the manifest's items, not its bytes. A failed stage stops with what to do and is not recorded; `--gate` also fails when a DATA-022 MVP line does not pass. Replaces the `fetch_<slug>.cmd` and `build_<slug>.cmd` launchers.
- `gen_content.py <pack_dir> [--config <json>] [--shots 5] [--dry-run]` (FEAT-175 step 4) generates the hand content Vail has by hand, from the pack alone, without a new build stamp (`write_meta(..., stamp=False)`, so a menu still of this build stays valid). **Start** (`meta.start`, `source: "generated"`, with `lift` and `label`): the top of the highest lift, on the config's `start_run` (matched without case, apostrophes or number words: "Four O'Clock" is OSM's "4 O'Clock") at the highest lift top it leaves, else on the most-ridden run leaving that top (most grooming reports, then groomed, intermediate before easy before advanced, then the longest; expert runs only when nothing else leaves it; the next lift down when none fits); walking down the run's centre line from 15 m below the top to the first point on snow (no rock or scree in the mask round it), clear of trees (no crown edge within 3 m, no stand over 0.25 within 6 m: `pack_report.py` line 10's rule), 20 m from any lift station, falling 4 to 35 degrees along the run and falling on (6 m over the next 60 m of its centre line, never rising 0.3 m above the start: on Big Sky the first try left the rider stopped in a flat). **Menu shots** (`attract/shots.json` and `attract/index.json` with `generated: true`, and `meta.attract`): camera spots 30 and 70 m past each lift's top station, on the named peaks inside the bounds and 40 and 80 m up the start run (those also 30 m up, to see out of a bowl), raised over the crowns round them (10 to 32 m); from each a panorama is ray-marched over the height sets (2 by 1.25 degree rays out to 40 km, fine then mid then far, with the earth's curvature) and every 10 degree heading and pitch is scored on terrain share (best 60 %), how far you see (the median and the far tenth of the hits, 300 m to 30 km on a log scale), less any slope blocking the upper half within 150 m and a lift station close by in the frame. The first shot, the menu's, is the best spot aimed at the start run with the run in view (weighted down past 120 m, as a rider there is a few pixels) whose view still scores at least 60 % of the best spot's; four more follow, best first, 250 m apart. Each is an `AttractShot` with a `note` giving its numbers. Every run writes the pack as if from scratch and records `meta.generated` (start found, shot count, the build's own start), which `build_resort.py` takes as the content stage done on this build: a run that finds no start puts the build's start back, and one that finds no shots removes an `attract/` an earlier run generated (a hand-made one stays). About 10 s on Boston Mills, 30 s on Breckenridge. The game's `tools/auto_attract.mjs` renders the still and rides the ghosts (its developer guide, Test tools > Generated resort content). Tests: `tests/test_gen_content.py`.
- `fetch.ps1` resumable Windows downloader (about 1.4 GB for Vail; `-RawDir` picks the destination), run by `build_resort.py` (or `powershell -File pipeline\fetch.ps1 -Slug <slug> [-RawDir <root>]` by hand). Run one fetch at a time.
- `fetch_static.ps1` (launcher `fetch_static.cmd`) Geofabrik Colorado OSM extract and USGS GNIS names into `raw/static/`.
- `placenames.py` (FEAT-235) place names for any US resort. `resort.py plan` records `names.states` in the config: every state whose box (Census cartographic boundaries, a little wide) meets the 200 km far ring, the resort's own first (Boston Mills: OH, MI, PA, WV; Big Sky: MT, ID, WY); a config without it gets the same list at manifest time. `gen_manifest.py` adds `names/DomesticNames_<ST>_Text.zip` (USGS GNIS) per state and the Census `<year>_Gaz_place_national.zip` and `sub-est<year>.csv` (places and their population). `build_pack.py` adds the GNIS summits OSM lacks to `peaks` (a summit with no height gets the highest ground near it) and, with no OSM `places_far`, the Census places as `labels` (city from 100,000 people, town from 10,000, else village; a CDP has no estimate and is a village). `pack_report.py` line 16 passes when `names/` holds GNIS and the pack has names. None outside the US.
- `fetch_landfire.mjs <slug> <email> [EVT|EVC|EVH] [--raw <raw_root>] [--force]` (launcher `fetch_landfire.cmd [slug] [raw_root]`, which fetches all three and asks for the slug when none is given) LANDFIRE clips via the LFPS job service: vegetation type (EVT) into `raw/<slug>/landfire/`, cover (EVC) and height (EVH, DATA-010) into `landfire/evc/` and `landfire/evh/`. A product already on disk is skipped unless `--force`.
- `fetch_grooming.py <slug> <raw_dir>` the resort's real grooming history (Vail's nightly reports, from Internet Archive snapshots of its terrain status page) into `raw/<slug>/grooming/`. Groomed runs in the pack come only from these reports and OSM `piste:grooming` tags.
- `extract_osm.py` cuts `osm/*.json` and `names/gnis.json` out of the static files (needs `pip install osmium`), the Overpass-free route for future resorts.
- `build_pack.py <slug> <raw_dir> <out_dir>` raw inputs to a resort pack (`pip install -r pipeline/requirements.txt`), about 4 minutes and 234 MB for Vail.
- `publish_pack.py <pack_dir> [--status preview|playable] [--tier gold|silver|bronze] [--report <md>] [--dry-run]` (FEAT-222) publishes a built pack from the main checkout on `main` (`gh` signed in with push access). Refuses a pack whose `meta.json` `formatVersion` is not `packwriter.FORMAT_VERSION` and a zip over 1.9 GiB. Zips the pack stored with fixed timestamps (the same pack gives the same sha256; `debug/` and dot files left out), creates release `<slug>-v<N>` (one past the highest release or catalog version) with the zip, `meta.json` and the report, then updates `catalog.json` with the resort's config, EPT node lists, manifest, data plan and report and commits them straight to `main`. `--synth` (FEAT-241) builds the synthetic pack and publishes it as test release `synth-v<N>` in the catalog's `test` list when its content changed. `status` comes from the pack's `report.json` (`pack_report.py`, below) when it was made for the pack's current `build`: `playable` when the report passes, `preview` otherwise or without one, and `--status playable` is refused unless the report passes (EPIC-15 rule 2). `--dry-run` zips and prints the catalog entry only. The game side is the game's `game/tools/get_pack.mjs` (`npm run get <slug>`; `npm run get -- --from <this repo>/packs/<slug>` copies an unpublished build in).
- `pack_report.py <pack_dir> [--raw <raw_dir>] [--config <json>] [--against <report.json>] [--gate]` (FEAT-175) the pack's scorecard on the DATA-022 new-resort checklist (#439), about 15 s for Vail. Writes `report.json` and `report.md` into the pack (or `--out`) and prints the markdown: one line per checklist item (F for the pack format, 1 to 14 and 8b MVP, 15 to 20 polish) as pass, warn, fail or skip, then the numbers behind them against Vail's (`REFERENCE`, or `--against` another report): rock, canopy and groomed shares, canopy left on run centre lines, crowns + stems per km² over the bounds and per 100 m band, crowns on lift lines, trees per hectare within 100 m of each compare spot, runs whose steepest 30 m pitch disagrees with their OSM difficulty, and whether the start is on snow, on a run and clear of trees. Line 17 (menu shot and ghosts) passes on the game's hand-made menu or on the pack's generated `attract/` with a still of this build and ghost takes (warns without them); line 19 counts compare spots with a Street View link apart from `propose_spots.py` proposals (proposals only: warn). `--raw` checks the raw files behind lines 2 to 4 and 16; without it those lines are judged from the pack (LANDFIRE, line 4, is then a skip unless the attribution credits it). The pack is playable when no MVP line is fail or skip; `--gate` exits 1 otherwise, and `publish_pack.py` reads the result. Run it after every build and paste `report.md` into the PR.
- `synth_pack.py <out_dir>` synthetic test mountain in the same format, for client work without real data.
- `packwriter.py` shared pack writer (Terrarium height tiles, masks) used by `build_pack.py` and `synth_pack.py`; every `meta.json` write stamps `build` and `pipeline` (the commit of the pipeline that wrote it, `+dirty` with uncommitted changes in `pipeline/`). `FORMAT_VERSION` (FEAT-222) is the pack format both builds write to `meta.json`; it must equal `PACK_FORMAT` in `game/src/pack/format.ts` (`pipeline/tests/test_contract.py` and `python pipeline/contract.py` check it against the game's `main`), and both are bumped on any pack-format change, the game first or together ([`pack-format.md`](pack-format.md) > formatVersion).
- `stands.py` (FEAT-074) stand density per 4 m cell: the stem chance from canopy, height and species less the detected crowns, and the `stands/` images ([`pack-format.md`](pack-format.md) > Stands), used by `build_pack.py`, `synth_pack.py` and `cover.py`.
- `terrain_ao.py` baked sky visibility (terrain ambient occlusion) from the DEM, used by the pack build.
- `coarse_set.py` (FEAT-229) the `coarse` height set, 4 m means of the 1 m mosaic over the fine area, written by `build_pack.py` and `synth_pack.py` right after the fine set; `python pipeline/coarse_set.py packs/<slug>` adds it to a built pack from its fine tiles (about 15 s for Vail, 36 tiles, 14 MB). The game's 4 and 8 m chunks read it instead of the fine tiles.
- `piste_dir.py` piste direction (DATA-002): the groomed runs' axis per 2 m cell as the `dir/` tile set, used by both pack builds; `python pipeline/piste_dir.py packs/<slug>` adds it to an existing pack from `features.json` and the mask tiles without a rebuild. The terrain (`Terrain.ts`) points it downhill and feeds it to the corduroy as the `fall` attribute, falling back to the smoothed fall line where a pack has no set.
- `cover.py <slug> <raw_dir> <pack_dir>` (FEAT-153) forest cover levels for the terrain at a distance (`cover/*.png`, see [`pack-format.md`](pack-format.md)): the pack's own canopy at 4 m with its OSM runs burned in and weighted by the drawn trees (BUG-069: R by their crown share for the view from far off, and a `stands` image with only the closed stands at least 40 m across for the near view, from the detected trees only (BUG-101), so sparse stands and small clumps stay snow with their trees; rerun it on a pack built before that), and (DATA-019) the mid (16 m, 40 km) and far (100 m, 200 km) levels from ESA WorldCover and the ETH canopy height with the pistes of every resort in view burned in. The pack level is built first and the mid and far forest is calibrated to it by WorldCover share and aspect (BUG-081), so the share does not jump at the pack edge; inside the far tree ring the mid and far forest comes from its lidar crowns instead (run `far_trees.py` first); rerun it on a built pack to get either. Runs as the last step of `build_pack.py`, or standalone on a built pack in seconds.
- `species.py` (DATA-020) tree species ids 0 to 9 (spruce, aspen, krummholz, fir, lodgepole, Douglas-fir, limber pine, snag; FEAT-233: bare hardwood and eastern hemlock) from the LANDFIRE class, elevation, aspect, distance to OSM streams, exposed crests and grey dead crowns, and the shrub set (willow, juniper, sagebrush, young conifer, Gambel oak); `build_pack.py` stage 8 calls it, logs per-species counts per 200 m elevation band and writes `debug/species.png` into the pack. Without a LANDFIRE clip it falls back to elevation and aspect. FEAT-233: east of 100 W (`region_for`) the eastern classes map to bare hardwood and hemlock, there is no aspen, and the fallbacks (no LANDFIRE, a class with no group, the far tree ring) are bare hardwood with hemlock below the boreal line; the log adds the LANDFIRE forest by group, its share in classes no rule names (`pack_report.py` line 4 warns over 20 %) and the species per group. LANDFIRE maps most of a ski area as `Urban Evergreen Forest` or `Developed-*`, which name no species (DATA-015): `natural_evt` gives each such pixel a natural forest class drawn from the stands within about 300 m, and NAIP breaks the tie there. Aspen is canopy brighter in visible and NIR than conifer, and lodgepole is canopy lower in NDVI than spruce-fir, both averaged over about 8 m. The thresholds are fitted per pack on its own natural LANDFIRE classes (`fit_aspen`, `fit_lodgepole`), so each resort's imagery calibrates itself. A fit that doesn't separate the two classes is not used: aspen then takes Vail's thresholds, and lodgepole gets no tie-breaker (Big Sky's NAIP has no lodgepole NDVI split). A pack without LANDFIRE uses Vail's aspen thresholds. The build log prints the fitted thresholds, their hit and false rates, and the class mix the built pixels were filled with. The client draws every id with its own species from the tree kit (FEAT-156); shrubs are not drawn yet (FEAT-159).
- `moguls.py` (FEAT-059) scores each run for mogul fields (grooming reports, difficulty, slope and aspect along the centre line, lift-top traffic; cat tracks, glades and greens never) and paints the amplitude raster the pack build writes as the `moguls` tile set. The build log lists the top-scoring runs. Tests: `python -m pytest pipeline/tests`.
- `ept_select.py <slug> [--dry]` picks the EPT lidar nodes over a resort for the manifest from its config: every node with points in `utm_bbox`, down to `lidar.max_depth_resort` where it touches the ski area (`lonlat_bbox`) and `max_depth_outside` elsewhere, for the main dataset and each of `lidar.extra`; writes each source's `nodes_file` (not with `--dry`). With `lidar.far` (`pad_m`, `max_depth`, `nodes_file`; BUG-081) it also picks the far tree ring's nodes (the box grown by `pad_m`, down to `max_depth`, less the main list), which `gen_manifest.py` sends to `raw/<slug>/ept_far/`.
- `far_trees.py <slug> <raw_dir> <pack_dir>` (BUG-081) the far tree ring: the lidar crowns on the ridges round the resort, outside the pack bounds, as `farTrees/` ([`pack-format.md`](pack-format.md) > Far tree ring). Runs inside `build_pack.py` before the cover when the config has `lidar.far` and the nodes are fetched, or standalone on a built pack (about 2 minutes and 3 GB for Vail's 5 km ring), followed by `cover.py`.
- `canopy_spots.py <pack> [--before <pack>] [--radius 80]` (BUG-028) canopy cover round the photo-pair spots in the game's `docs/compare/<slug>/`, from the mask alpha: over the whole disc and over its off-run part (non-glade run corridors, roads and buildings left out, with the run widths `build_pack.py` cuts the forest with, `RUN_HALF_WIDTH`). Checks the BUG-028 targets (off-run canopy at least 0.5 within 80 m of Born Free and 100 m of Mid-Vail; with `--before`, the open bowls gain no more than 0.02) and exits 1 if one fails. Where the pack has tree instances it also lists the live detected crowns (snags left out) per hectare of the disc's off-run ground (DATA-011). Run it after a rebuild that touches the canopy rules or the crown detection.
- `naip_calib.py` (FEAT-175) the NAIP canopy and rock thresholds for the resort being built, from its own imagery. Vail's values (NDVI, grey saturation, shadow brightness) each keep the percentile they sit at on Vail, read on two lidar-defined anchors: forest (canopy over 8 m) and low bare ground (under 0.3 m, below the forest's median elevation). A threshold moves only when both anchors move it the same way, by the smaller move; moves under 3 % keep Vail's value, and every value stays in an absolute range (snow, brightness over 215, stays absolute). Vail gets its own values back; Big Sky's darker, greyer 2021 NAIP gets a grey test of 0.093 instead of 0.20. `build_pack.py` stage 5 logs each value and both anchors' candidates and writes them to `meta.json` `derived`; a config `naip_thresholds` (`{"rock.grey_sat": 0.12}`) overrides one.
- `treeline.py` (DATA-021) the resort's treeline from its own canopy by elevation (where the canopy share falls under half its peak), written to `meta.json` as `treeline`; the build also shifts the species' elevation bands (tuned on Vail's 3,480 m) by the difference, and the client puts its procedural treeline, open valley floor and snow-ghost band there (the game's `game/src/pack/treeline.ts`). Where the box is forest from the bottom to the top (Boston Mills) it writes `treeline: null` (FEAT-234, `forested_to_top`): no snow-ghost band and no elevation opening in the client. No forest belt to measure writes nothing, which keeps Colorado's. On the raw on disk (2026-11-12) the derivation gives Vail 3,550 m, Breckenridge 3,525 m and Big Sky 2,700 m; the Vail and Breckenridge packs on disk predate DATA-021 and carry none yet.
- `osm_filter.py` (DATA-021) drops private runs and lifts (the config's `exclude` areas and `access=private` tags) from `osm/ski.json` before the build reads it.

The data hosts (USGS, Planetary Computer, Overpass, Mapterhorn) are not reachable from cloud sandboxes; fetching runs on Drew's PC. Before touching raw data read the game's [`docs/data/vail-raw-data-inventory.md`](https://github.com/drewkeriazes/SnowboardAnywhere/blob/main/docs/data/vail-raw-data-inventory.md) (written when the pipeline lived there). Pack layout: [pack-format.md](pack-format.md).
