# MapPacker-SnowboardAnywhere: working notes for Claude

**This repo builds the resort packs; SnowboardAnywhere (the game) just plays them** (EPIC-16, #9; plan in `docs/pipeline-move.md`). A resort name goes in, a published pack comes out: `pipeline/` turns a config into a pack, `publish_pack.py` puts the pack out as a release here and adds it to `catalog.json`, and the game's `npm run get <slug>` downloads it.

- Stack: Python 3.13 (numpy/scipy/pillow/tifffile/pyproj/shapely/laspy, `pipeline/requirements.txt`); PowerShell fetch scripts (`pipeline/fetch.ps1`, `pipeline/fetch_static.ps1`) and `pipeline/fetch_landfire.mjs` (Node) run on Drew's PC with no installs. Launchers in the repo root: `add_resort.cmd "<name>"` (FEAT-224: name to published pack), `build_resort.cmd <slug>` (FEAT-175: config to scored pack), `fetch_static.cmd`, `fetch_landfire.cmd`. Skill: `.claude/skills/pack-build/`.
- Layout (`pipeline/paths.py` is the one place that knows it): a folder per resort, `resorts/<slug>/`, with its config `<slug>.json`, the EPT node lists it names and its data plan (`paths.resort_dir`, `paths.config_path`); download manifests in `manifests/`; packs build to `packs/<slug>/`; build reports in `reports/`; `catalog.json` lists what is published. One home per file: the pipeline reads and writes these directly, there are no copies.
- Flow: `resort.py resolve` / `plan` -> `resorts/<slug>/<slug>.json` -> `gen_manifest.py` -> `manifests/<slug>.json` -> `fetch.ps1` -> `<raw root>/<slug>/` -> `build_pack.py` -> `packs/<slug>/` -> `pack_report.py` (the DATA-022 scorecard) -> headless ride in the game -> `publish_pack.py`. `build_resort.py` runs the middle and skips every stage whose inputs have not changed (`<raw>/build_resort.json`); `resort.py add` runs all of it.
- Raw data never goes on GitHub. It lives at `SBA_RAW_ROOT`, else `raw/` in the main checkout (worktrees share it). On Drew's PC `SBA_RAW_ROOT` points at `C:\Users\Drew\git\SnowboardAnywhere\raw` until the data (many GB) is moved. Do not run two fetches at once; the downloader assumes one writer. Data hosts (USGS, Planetary Computer, Overpass, Mapterhorn, usgs-lidar-public, LFPS) are reachable only from Drew's PC, not the cloud sandbox.
- The game is a sibling clone, `C:\Users\Drew\git\SnowboardAnywhere` (found at `../SnowboardAnywhere` next to the main checkout; `--game-repo` or `SBA_GAME_REPO` overrides). The pipeline needs it only for the ride stage (`npx vite build` and `game/tools/shoot.mjs`), `pack_report.py`'s game-side lines (attract shots, landmarks, compare spots, `resorts.ts`, until FEAT-243 moves them into the pack) and the tests that compare with a game file (they skip without it). Missing game: those say so and stop or skip.
- The pack format is the contract between the repos. The spec is `docs/pack-format.md` here (FEAT-239); its Contract section lists every value both sides hold, with file and line on each side (`FORMAT_VERSION` in `pipeline/packwriter.py`, `PACK_FORMAT` in the game's `game/src/pack/format.ts`, species crown radii, the default treeline, `packs/index.json`, `catalog.json`). A change a current game can't read bumps it, and the game's PR lands first or together. `pipeline/tests/test_contract.py` (and `python pipeline/contract.py`) compare with the game's `main` on GitHub: this repo ahead fails, offline skips with a warning; `SBA_GAME_REPO=<game worktree>` checks the pair before either lands.
- Packs live in releases, never in git history. `publish_pack.py` runs in the main checkout on `main` and commits the catalog and the resort's own files straight to `main`; that is the one commit that does not go through a PR. Packs published before FEAT-238 name a SnowboardAnywhere commit in `pipeline`; after it, a commit here.
- Checks: `python -m pytest pipeline/tests` before pushing (about 5 s; `SBA_NETWORK=1` adds the tests that plan real resorts against the data hosts). The Claude PR reviewer (`.github/workflows/pr-review.yml`, rules in `.claude/agents/pr-reviewer.md`) comments on every PR, and `pr-feedback.yml` applies the items Drew answers "yes" to, as in the game repo. CI checks arrive with FEAT-240; until then say in the PR what you ran. A pipeline change can change what the game draws: for one that does, render the pack in the game on Drew's GPU and say so in the PR.
- Board and PRs: the same board and rules as the game, `docs/BOARD.md` in SnowboardAnywhere. "Build FEAT-238" means: a worktree and branch `issue-<number>-<slug>` from `origin/main` (`git worktree add ../wt-mp<number> -b issue-<number>-<slug> origin/main`), commit with the card id in the message, open a PR with `Fixes #<number>`, Drew reviews and merges. Never push to `main` directly (publishing aside). Card ids are one sequence across both repos: `python ../SnowboardAnywhere/tools/card_id.py` before and after making a card, and write `SnowboardAnywhere#<n>` for a game issue. A problem found along the way gets its own card, after searching both repos for one.
- Commit messages: plain, no `Co-Authored-By` or session-link trailers. Commits are authored as Drew. No em dashes in prose.
