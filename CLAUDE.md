# MapPacker-SnowboardAnywhere: working notes for Claude

**This repo builds the resort packs; SnowboardAnywhere (the game) just plays them** (EPIC-16, #9; plan in `docs/pipeline-move.md`). A resort name goes in, a published pack comes out: `pipeline/` turns a config into a pack, `publish_pack.py` puts the pack out as a release here and adds it to `catalog.json`, and the game's `npm run get <slug>` downloads it.

- Stack: Python 3.13 (numpy/scipy/pillow/tifffile/pyproj/shapely/laspy, `pipeline/requirements.txt`); PowerShell fetch scripts (`pipeline/fetch.ps1`, `pipeline/fetch_static.ps1`) and `pipeline/fetch_landfire.mjs` (Node) run on Drew's PC with no installs, and under `pwsh` on the Linux runner. Launchers in the repo root: `add_resort.cmd "<name>"` (FEAT-224: name to published pack), `build_resort.cmd <slug>` (FEAT-175: config to scored pack), `fetch_static.cmd`, `fetch_landfire.cmd`. Skill: `.claude/skills/pack-build/`.
- Layout (`pipeline/paths.py` is the one place that knows it): a folder per resort, `resorts/<slug>/`, with its config `<slug>.json`, the EPT node lists it names and its data plan (`paths.resort_dir`, `paths.config_path`); download manifests in `manifests/`; packs build to `packs/<slug>/`; build reports in `reports/`; `catalog.json` lists what is published. One home per file: the pipeline reads and writes these directly, there are no copies. In a config, `utm_bbox` is the box the raw data is fetched for and `pack_bbox` (FEAT-249, default `utm_bbox`) the box the pack is built on; `relocate` pastes a far area next to the rest (`pipeline/relocate.py`, Boston Mills / Brandywine); a move with `source` cuts from another place's raw data, a `source_only` config, and `raw_from` builds on another resort's raw folder (FEAT-268, Ohio Hills: Boston Mills plus Mad River).
- Flow: `resort.py resolve` / `plan` -> `resorts/<slug>/<slug>.json` -> `gen_manifest.py` -> `manifests/<slug>.json` -> `fetch.ps1` -> `<raw root>/<slug>/` -> `build_pack.py` -> `packs/<slug>/` -> `published.py` (FEAT-293: the resort's published figures, `resorts/<slug>/<slug>-published.json`) -> `pack_report.py` (the DATA-022 scorecard; line 21 checks the pack against those figures) -> `publish_pack.py` (a draft release and a publish PR); the headless ride in the game runs only with `resort.py add --ride`. `build_resort.py` runs the middle and skips every stage whose inputs have not changed (`<raw>/build_resort.json`); `resort.py add` runs all of it. In GitHub Actions, `build-pack.yml` (FEAT-245) runs it for one slug on a free hosted runner, a queue and a data-host probe first, and ends in the same publish PR (README > Build in GitHub Actions); `publish_pack.py` publishes nothing when the pack's `content` hash matches the catalog's or an open publish PR's.
- Raw data never goes on GitHub. It lives at `SBA_RAW_ROOT`, else `raw/` in the main checkout (worktrees share it). On Drew's PC `SBA_RAW_ROOT` points at `C:\Users\Drew\git\SnowboardAnywhere\raw` until the data (many GB) is moved. Do not run two fetches at once; the downloader assumes one writer. Data hosts (USGS, Planetary Computer, Overpass, Mapterhorn, usgs-lidar-public, LFPS) are reachable only from Drew's PC, not the cloud sandbox.
- The game is a sibling clone, `C:\Users\Drew\git\SnowboardAnywhere` (found at `../SnowboardAnywhere` next to the main checkout; `--game-repo` or `SBA_GAME_REPO` overrides). The pipeline needs it only for the ride stage (`npx vite build` and `game/tools/shoot.mjs`), `pack_report.py`'s game-side lines (attract shots, landmarks, compare spots, `resorts.ts`, until FEAT-243 moves them into the pack) and the tests that compare with a game file (they skip without it). Missing game: those say so and stop or skip.
- The pack format is the contract between the repos. The spec is `docs/pack-format.md` here (FEAT-239); its Contract section lists every value both sides hold, with file and line on each side (`FORMAT_VERSION` in `pipeline/packwriter.py`, `PACK_FORMAT` in the game's `game/src/pack/format.ts`, species crown radii, the default treeline, `packs/index.json`, `catalog.json`). A change a current game can't read bumps it, and the game's PR lands first or together. `pipeline/tests/test_contract.py` (and `python pipeline/contract.py`) compare with the game's `main` on GitHub: this repo ahead fails, offline skips with a warning; `SBA_GAME_REPO=<game worktree>` checks the pair before either lands.
- Packs live in releases, never in git history. `publish_pack.py` (FEAT-272) runs from any checkout and nothing in it pushes to `main`: it refuses a pack whose `meta.json` `pipeline` stamp is missing, `+dirty` or not on origin/main, uploads a draft release `<slug>/v<N>` (FEAT-271: `vail/v4`; type `vail/` in the Releases search, and `RELEASES.md` lists every resort's versions, rewritten in each publish PR by `pipeline/releases.py`), and opens a PR `publish/<slug>-v<N>` labelled `publish` with the catalog entry, `reports/<slug>.md` and the resort's own files. The `publish-check` job downloads the draft zip and checks size, sha256 and the pack lint (`pack_lint.py`: 600 MB, 5,000 files, 80,000 trees per km2). `publish-merge.yml` publishes the draft and then squash-merges, with the GitHub App token, a trusted publish PR (publisher in `.github/maintainers.txt`, so `automerge` is added) whose checks are green and that changes only the publish file set. Approve a publish with the `automerge` label, never the merge button (the draft must be released first). A pack with a changed look gets `--accept-change` and the `accept-change` label (FEAT-264, not yet enforced). `publish-merge.yml` also runs every 15 minutes and each run looks at every open `automerge` publish PR, so none is stranded; a closed, unmerged publish PR loses its draft and its branch. Setup Drew owns: the GitHub App "MapPacker publisher" on this repo (Contents and Pull requests: write; Issues, Actions, Checks and Metadata: read), secrets `PUBLISH_APP_ID` and `PUBLISH_APP_KEY`, variable `PUBLISH_APP_LOGIN`. Until the App, its secrets and the variable exist, nothing merges itself; the safe manual path is `gh release edit <tag> --draft=false` first, then merge the PR (never the merge button with the release still a draft). A publish PR whose branch predates a workflow-file change on main needs a hand refresh: merge main into the branch locally and push, then remove and re-add the `automerge` label (a push after the label by anyone but the App is refused as untrusted). After a NEW resort's publish PR merges, its `resorts/<slug>/` and `manifests/<slug>.json` are still untracked in the checkout that published, so `git pull` there refuses: delete those untracked copies (they are what merged), then pull. Packs published before FEAT-238 name a SnowboardAnywhere commit in `pipeline`; after it, a commit here. The synthetic pack the game's CI runs on is a test pack in the catalog's `test` list (not the picker), release `synth/v<N>`: after merging a pipeline or format change, run `python pipeline/publish_pack.py --synth` from a checkout of the merged `main` (it builds it and opens a publish PR only when the content changed; FEAT-241, FEAT-272). A format bump publishes the new-format synth beside the old one, so the game's `main` keeps working until its own bump lands.
- Checks: `python -m pytest pipeline/tests` before pushing (about 5 s; `SBA_NETWORK=1` adds the tests that plan real resorts against the data hosts). CI (`.github/workflows/checks.yml`, README > Checks) runs pytest, the `format-check` (`pipeline/contract.py` and the tests marked `game`, against the game's `main`; there a missing game file fails instead of skipping), `render-budgets` (the game's `main` drawing the synthetic pack from `main` and from the PR), repo rules and public guards; the reviewer treats a failed check as blocking. On Drew's PC `node tools/ci/local_render_budgets.mjs`, or the pre-push hook (`git config core.hooksPath .githooks` and `git config sa.gpuBudgets true`), runs `render-budgets` on the GPU and CI skips it for that commit. The Claude PR reviewer (`.github/workflows/pr-review.yml`, rules in `.claude/agents/pr-reviewer.md`) comments on every PR, and `pr-feedback.yml` applies the items Drew answers "yes" to, as in the game repo. A pipeline change can change what the game draws: for one that does, render a real pack in the game on Drew's GPU too and say so in the PR.
- Board and PRs: the same board and rules as the game, `docs/BOARD.md` in SnowboardAnywhere. "Build FEAT-238" means: a worktree and branch `issue-<number>-<slug>` from `origin/main` (`git worktree add ../wt-mp<number> -b issue-<number>-<slug> origin/main`), commit with the card id in the message, open a PR with `Fixes #<number>`, Drew reviews and merges. Never push to `main` directly; a publish goes through its own PR too (above). Card ids are one sequence across both repos: `python ../SnowboardAnywhere/tools/card_id.py` before and after making a card, and write `SnowboardAnywhere#<n>` for a game issue. A problem found along the way gets its own card, after searching both repos for one.
- Commit messages: plain, no `Co-Authored-By` or session-link trailers. Commits are authored as Drew. No em dashes in prose.
